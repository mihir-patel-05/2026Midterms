# Day 0 database foundation

**Status:** implemented as an additive Prisma schema and migration on September 21, 2026.

## Purpose and boundaries

The new tables provide a provider-neutral foundation for election events, contests, stable people and candidacies, geography, reporting units, immutable result snapshots, source provenance, ingestion operations, and certification history.

No nationwide result provider is represented or implied. Provider records default to disabled (`DataSource.isEnabled = false`), and mock records carry `isMock = true` at the source, raw-artifact, and result-snapshot layers. The included fixture uses the invalid jurisdiction code `ZZ`, fictional names, reserved `example.invalid` URLs, and prominent mock notices.

The existing `Candidate`, `Election`, `CandidateElection`, `County`, and `CountyResult` models are preserved. Optional bridge keys allow a later reviewed backfill without changing existing public reads:

- `Contest.legacyElectionId` → existing `Election.id`
- `Candidacy.legacyCandidateId` → existing `Candidate.id`
- `Candidacy.legacyCandidateElectionId` → existing `CandidateElection.id`

## Model map

| Concern | New models | Key design choice |
|---|---|---|
| Source registry | `DataSource` | Explicit attribution, license fields, health, enablement, and mock status |
| Election identity | `ElectionEvent`, `Contest` | Event and individual race are separate; office names remain provider-neutral strings |
| Candidate identity | `Person`, `Party`, `Candidacy` | A person is stable across contests; ballot and FEC statuses remain contest-specific |
| Geography | `GeographyVersion`, `GeographyUnit`, `GeographyRelation` | Versioned units and explicit `CONTAINS`/`INTERSECTS` relationships support county–district overlap |
| Provider reporting units | `ReportingUnit` | Provider unit IDs are mapped independently to normalized geography |
| Ingestion operations | `IngestionRun`, `IngestionError`, `RawArtifact` | Parser version, counters, immutable artifact hash/storage key, and record-level errors remain auditable |
| Results | `ResultSnapshot`, `CandidateVote`, `ContestMetric` | Snapshots are append-only; vote counts use `BIGINT`; provider percentages are optional audit values |
| Publication | `Contest.currentSnapshotId` | The public snapshot can be changed atomically without overwriting history |
| Certification | `CertificationEvent` | Unofficial, canvassing, certified, recount, contested, and correction history remains separate from reporting progress |

Election-night results can remain unofficial even when every precinct is reporting, so `ReportingStatus` and `CertificationStatus` are deliberately independent. See the [U.S. Election Assistance Commission’s canvass and certification overview](https://www.eac.gov/election-officials/election-results-canvass-and-certification). Reporting units and source-supplied subunit counts align with the concepts in the [NIST Election Results Reporting Common Data Format](https://pages.nist.gov/ElectionResultsReporting/).

## Important invariants

Application and ingestion code must enforce the following when it is added:

1. Publish a snapshot only after its candidates, units, votes, metrics, artifact, and validation results are committed in the same transaction.
2. Set `Contest.currentSnapshotId` only to a `PUBLISHED` snapshot belonging to that same contest. The relational schema guarantees a valid snapshot ID, while the same-contest/publication-status rule is intentionally enforced by the publication transaction.
3. Never replace the current snapshot with an empty or failed ingestion response.
4. Treat `CandidateVote.sourceVotePercentage` and `ContestMetric.reportingPercentage` as source-reported audit values. Public percentages should be derived from vote totals where semantics permit and discrepancies should be logged.
5. Do not aggregate child and parent reporting-unit totals together; they can represent the same votes at different geographic levels.
6. Preserve vote decreases and other provider corrections as a new snapshot rather than mutating prior snapshots.
7. Set `BALLOT_CONFIRMED` only from an approved ballot authority. An FEC record by itself maps to `FEC_FILED`, not ballot confirmation.
8. Keep mock sources disabled outside an explicit mock/replay mode and propagate `isMock` to every API response using them.
9. Store only sanitized public source URLs; credentials and signed object-storage URLs must never be persisted in these fields.

## Migration

Migration: `backend/prisma/migrations/20260921120000_day0_election_results_foundation/migration.sql`

The migration is additive: it creates enums, tables, indexes, and foreign keys only. It does not alter, delete, rename, or backfill an existing table. It was generated by diffing the checked-in pre-Day-0 Prisma schema against the updated schema, which avoids unrelated drift.

Production apply command from `backend/`:

```bash
npm run prisma:deploy
```

Run the migration once from the API/pre-deploy job, not concurrently from web and worker replicas.

### Rollback and forward-fix plan

Prisma migrations do not include automatic down migrations. The preferred response after any environment has written real normalized results is a forward-fix migration that preserves source artifacts and snapshots.

Before any new-table data exists, a manual rollback is possible because the change is isolated from existing rows. Drop in this dependency order:

1. `certification_events`, `contest_metrics`, `candidate_votes`
2. Clear `contests.current_snapshot_id`, then drop `result_snapshots`
3. `ingestion_errors`, `raw_artifacts`, `ingestion_runs`
4. `candidacies`, `people`, `parties`
5. `reporting_units`, `geography_relations`
6. Clear geography references, then drop `contests`, `geography_units`, `geography_versions`, `election_events`, `data_sources`
7. Drop the new enums only after every dependent table is gone

Do not run that rollback after provider or mock-rehearsal artifacts must be retained. Take a database backup first and prefer disabling the dashboard/provider feature flags plus moving `currentSnapshotId` to the last known-good snapshot.

## Fictional fixture

`backend/prisma/fixtures/day0-provider-neutral.mock.json`

Idempotent SQL seed:

`backend/prisma/fixtures/day0-provider-neutral.mock.sql`

The fixture represents a fictional November 3 election with partial, unofficial results reported and ingested at `2026-11-04T02:15:00Z`. The JSON SHA-256 is `150662974f61fd342c05b05332c57f7d141eda721a7cf8d8b3a3650cce84139e` and is recorded by the seed as both the raw artifact hash and snapshot payload hash.

Apply only to a disposable local/test database after migrations:

```bash
psql "$DATABASE_URL" --set ON_ERROR_STOP=1 --file prisma/fixtures/day0-provider-neutral.mock.sql
```

The seed is wrapped in one transaction and uses deterministic IDs with `ON CONFLICT DO NOTHING`, so replaying it does not duplicate results. It is not wired into production startup or the existing seed path.

- Decide the authoritative 2026 Census geography vintage and build hash before inserting production `GeographyVersion` rows.
- Define the candidate/person matching review workflow. Ambiguous matches must not be guessed.
- Define parser-specific vote-type normalization while preserving the original provider label in ingestion metadata.
- Decide whether an approved provider supplies stable snapshot IDs. Payload hashes already provide idempotency when it does not.
